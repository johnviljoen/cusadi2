# Safe MPPI on the Panda: 256 CBF-filtered 2 s rollouts per tick in 31 ms with cusadi2, 191-274 ms with the GPU frameworks, 26 ms on 16 CPU threads

**Status (2026-10-16).** This directory is the one-iteration best-sample variant of `examples/panda_safe_mppi` (safe
predictive sampling: the best of the K CBF-filtered rollouts becomes the plan and its first filtered torque is applied,
nothing averaged, nothing re-filtered; `FORMULATION.md`, `driver.py`, `closed_loop.py`). Its closed loop failed the
no-tuning pass rule on every seed: the arm stalls against the sphere at the first waypoint because no single
perturbation of the plan beats it there (the plan was kept on 71-81 % of the ticks; `results/closed_loop_ps*.json`,
`results/closed_loop_ps.mp4`). The MJPC-faithful successor, with several sequential planner iterations per tick, MJPC's
cubic 7-knot spline, noise scaling and sizes, is `examples/panda_safe_mjpc`. The README below is still the MPPI
example's text and is kept only as the description of the shared driver and evaluators.


The batched backup-CBF filter of `examples/panda_backup_cbf` needs a consumer that must be real time. This example
makes the one-step CBF filter the safety layer inside every rollout of a sampling-based MPC: one Franka Panda,
MPPI with K = 256 sampled joint-target plans over T = 100 steps of 20 ms (a 2 s horizon), and at every rollout step the sampled torque is
projected onto the CBF rows of frax's demo scene (64 barriers: joint limits, singularity, obstacle, self-collision,
floor) before the dynamics step. The sampler only sees safe trajectories, the applied torque is filtered the same way,
and there is no QP and no linear solve anywhere, so the control tick is model evaluation. The formulation is in
`FORMULATION.md`.

One native CUDA MPPI driver (`safe_mppi.cu`: sampling, the projection kernel, weighting, plant step, one CUDA graph per
tick) with a pluggable model evaluator, the only part that differs between the rows. Every fp64-capable framework of the
paper's function-level benchmarks is a row, plus frax, the stack the demo is built on (MuJoCo Warp is fp32-only and has no
fp64 row):

| evaluator | model(x, Y, rp, par) -> (u_nom, G, h) and integrate(x, u, rp, par) -> x1 |
|---|---|
| cusadi2 | two CasADi functions (Pinocchio-casadi on frax's URDF, cbfpy's row algebra with `jtimes`) compiled to level-parallel plans, launched by the driver |
| frax + cbfpy (JAX/XLA) | the unmodified frax robot and cbfpy rows in JAX, `jax.export`ed to StableHLO and run by the same driver through JAX's own CUDA PJRT plugin on views of the driver's buffers |
| MuJoCo XLA + cbfpy (JAX/XLA) | the same equations with MJX's kinematics, CRB mass matrix, RNE bias and Jacobian (`mjx_model.py`; the MJCF is generated from the Pinocchio model of the URDF because MuJoCo's URDF importer drops the inertia of the massless `panda_link8`), cbfpy rows, exported and run the same way |
| CusADi (original) | the same two CasADi functions as the original CusADi's one-thread-per-instance unrolled kernels (`cusadi2.unrolled` codegen, nvcc), launched by the driver |
| CasADi C codegen, CPU | the same two functions through CasADi's C code generation (gcc -O3 -march=native), 16 OpenMP threads over the rollouts, with the GPU -> CPU -> GPU transfer of every call ("CPU + transfer"; the MPPI's own kernels stay on the GPU) |

All five compute the same controller: on identical ticks (same seed, state, plan) the applied torque and the recorded
100-step rollout trajectories agree with the cusadi2 run to 1e-14 (CusADi original, CPU) and 1e-9 (frax, MJX)
(`verify_evaluators.py`; the per-call agreement of MJX with frax is 1e-14, `mjx_model.py`).

Results (`results/report.md`, generated by `report.py`; RTX 4080 + Ryzen 5800X3D, fp64):

| K = 256, T = 100 (2 s) | tick median | tick p99 | model call | integrate call | projection (shared) |
|---|---:|---:|---:|---:|---:|
| cusadi2 | 30.9 ms | 35.8 ms | 0.244 ms | 0.054 ms | 0.054 ms |
| frax + cbfpy (JAX/XLA) | 201.6 ms | 203.4 ms | 1.716 ms | 0.214 ms | 0.054 ms |
| MuJoCo XLA + cbfpy (JAX/XLA) | 274.1 ms | 278.4 ms | 2.292 ms | 0.344 ms | 0.054 ms |
| CusADi (original) | 190.8 ms | 195.9 ms | 1.718 ms | 0.182 ms | 0.054 ms |
| CasADi C codegen, CPU 16 threads + transfer | 25.6 ms | 41.1 ms | 0.189 ms | 0.034 ms | 0.054 ms |

Against the GPU frameworks cusadi2 is 6.5x (frax), 8.9x (MuJoCo XLA) and 6.2x (the original CusADi) faster on the tick,
7-9x on the model call; model evaluation is 85 % of our rollout step. The CPU row is the finding to report rather than
hide: on this machine (Ryzen 5800X3D, 16 threads, 96 MB L3) CasADi's generated C evaluates the model for 256 rollouts in
0.13 ms of compute (3.9 us per instance single-threaded) and 0.19 ms with the GPU -> CPU -> GPU transfer of every call, so
its tick is 26 ms median against our 31 ms, with a worse tail (p99 41 vs 36 ms) and all 16 threads busy for the whole
tick. This is the deep-and-narrow regime of the paper's Q2: the model function is 30.5k nodes in 207 levels, about 150
nodes per level, so cusadi2's one-block-per-rollout kernel pays its depth, and 256 rollouts are only 256 blocks. In the
K sweep at T = 100 the two are equal at K = 512 (44 vs 47 ms) and cusadi2 is ahead from K = 1024 on (72 vs 89 ms, 134 vs
170 ms at 2048), where the CPU's linear scaling meets the GPU's. The horizon was set to 2 s for the video (the sampled
plans then reach the waypoint); at that horizon cusadi2 runs at 30 Hz, the GPU frameworks at 4-5 Hz. The pass test fixed
in advance (ours p99 <= 16 ms and frax >= 30 ms at the same K and T, the 50 Hz budget) holds up to T = 50 (1 s: 15.4 ms vs
102 ms); frax leaves the 20 ms budget at K = 256 for every T >= 10, cusadi2 stays under it up to T = 50 at K = 256 and up
to K = 128 at T = 100.

## Pieces

| file | what |
|---|---|
| `model.py` | CasADi `model` and `integrate` functions, the parameters, and the numpy reference of the projection kernel |
| `frax_model.py` | the frax + cbfpy twin in JAX and its `jax.export` to StableHLO |
| `mjx_model.py` | the MuJoCo XLA + cbfpy twin (MJCF generated from the Pinocchio model), its check against frax and its export |
| `verify.py` | gate 1: CasADi vs JAX (5e-12 relative), the projection kernel vs its reference (1e-15) |
| `verify_evaluators.py` | gate 1b: every evaluator against cusadi2 on identical ticks (applied torque, rollout trajectories, weights) |
| `build.py` | plans (`build/plans`), exported programs and JAX's compile options (`build/programs`), the original-CusADi kernels (`build/unrolled`), the CPU codegen libraries (`build/cpu`), the driver library |
| `safe_mppi.cu`, `driver.py` | the native driver with the five evaluators, and its ctypes front end |
| `smoke.py`, `bench.py`, `report.py` | model-plant runs, the K / T sweeps, the report and plot |
| `closed_loop.py` | the MuJoCo closed loop with video, safe MPPI or the filtered OSC |
| `projection_study.py` | the shared filter against cbfpy's elastic QP on 20-step rollouts |
| `dataset.py` | test inputs (states from `profiling/sampling.py`) |

Build and run order: `verify.py` -> `build.py plans` -> `build.py export --backend frax mjx` -> `build.py unrolled` ->
`build.py cpu` -> `build.py lib` -> `verify_evaluators.py` -> `bench.py` -> `closed_loop.py --controller mppi --frax-timing`
and `--controller osc` -> `projection_study.py` -> `report.py`.
frax and cbfpy are the unmodified versions of `profiling/` (pinned frax commit, pip cbfpy 0.1.0 / qpax 0.1.4).

## What was learned on the way (kept because it shapes the design)

- cusadi2's level kernel runs one thread block per instance and pays one block barrier per level of the expression
  graph. At K <= 128 a call costs its depth, not its arithmetic (207 levels, 0.12 ms); from K = 256 the SMs are shared
  and the call grows roughly linearly (0.24 ms at 256, 1.14 ms at 2048), while XLA is launch-bound at this batch (1.7 ms)
  and the original CusADi's one thread per instance leaves the GPU almost empty (1.7 ms, flat up to 2048). At thousands
  of instances per launch the advantage over XLA shrinks (an earlier multi-robot variant of this example, 256 robots x K
  samples, measured 1.3x in fp32 and was abandoned).
- The CPU is a real competitor for this function shape. CasADi's generated C (gcc -O3 -march=native) runs one instance of
  the 30.5k-node model function in 3.9 us on one core of the 5800X3D; 16 threads cover 256 rollouts in 0.13 ms, and the
  transfer of every call (inputs device -> host, outputs host -> device, a stream synchronisation in between) adds only
  60 us, because the data of a call is 1.2 MB and lives in pinned memory. The CPU row's weaknesses are the tail (OS
  scheduling: p99 1.6x the median) and that it occupies the whole CPU; its strength is that a deep graph costs it nothing
  extra. The timing of the CPU row is only valid on an otherwise idle machine: measured while nvcc and the JAX exports
  were running it read 60 ms median and 500 ms p99.
- A projection written inside the CasADi graph is the wrong shape for that kernel: 32 greedy iterations are 2800
  levels and made cusadi2 2.3x slower than frax. The filter is therefore a separate CUDA kernel of the MPPI (one warp
  per rollout, 55 us for 256), shared by both evaluators, and the evaluator is pure model evaluation.
- An exact small-active-set projection (three most violated rows, closed-form KKT) was tried for the in-graph version:
  nearly parallel rows (neighbouring obstacle spheres) make its exact solution jump far from the nominal torque in
  infeasible situations and it let 4 % of rollouts breach a barrier where cbfpy's QP lets none. The greedy filter with
  32 or more iterations matches the QP on that metric (`projection_study.py`).
- fp32: XLA's fp32 on a consumer GPU is 5.5x its fp64, cusadi2's level kernel gains 2.9x, so the fp32 ratio collapses
  to about 1.3x. As in the two earlier demos, the claim is an fp64 claim.
- PJRT embedding: `jax.export` with `keep_unused=True` (jit prunes unused arguments otherwise), the plugin created with
  `preallocate=false`, buffer views need a no-op delete callback and `stream = 0` plus a host synchronisation, since the
  GPU client only accepts its own DLPack streams as a view's producer stream.

# Safe MPPI on the Panda: one robot, 256 CBF-filtered rollouts per tick, fp64, 50 Hz

Generated by `report.py`. RTX 4080 + Ryzen 5800X3D, fp64, one native CUDA MPPI driver, five model evaluators (cusadi2 plans; frax + cbfpy and MuJoCo XLA + cbfpy as jax.export'ed programs through PJRT; the original CusADi's unrolled kernels of the same CasADi functions; CasADi's C code generation on the CPU with the GPU <-> CPU transfer of every call), identical sampling, projection, weighting and plant code. Tick = everything between two control outputs, CUDA events on the driver's stream, median and p99 over 60 ticks on the model plant; pieces timed alone on the sample buffers. MuJoCo Warp, the paper's fourth GPU baseline, is fp32-only and has no row for this fp64 study.

The projection column is the cusadi2 run's measurement of the shared kernel: its cost depends on the data left in the sample buffers (it exits early when no row is violated), and only the capturable evaluators leave the last rollout step there.

Speed-up of cusadi2 over frax + cbfpy (JAX/XLA): tick 6.5x, model call 7.0x, integrate call 3.9x; MuJoCo XLA + cbfpy (JAX/XLA): tick 8.9x, model call 9.4x, integrate call 6.3x; CusADi (original, one thread per instance): tick 6.2x, model call 7.1x, integrate call 3.3x; CasADi C codegen, CPU 16 threads + transfer: tick 0.8x, model call 0.8x, integrate call 0.6x.
The model and integrate calls are 85 % of our rollout step (97 % of frax's).

CPU idealized (the same CasADi C code, 16 threads, no transfer, K = 256): model call 0.128 ms, integrate call 0.016 ms, T = 100 rollout 15.2 ms; with the GPU <-> CPU transfer of every call: 0.186 / 0.033 ms, rollout 24.0 ms. The MPPI's sampling, projection, weighting and plant step run on the GPU, so the tick of the CPU row is the transfer variant.

Pass test fixed in advance (ours p99 <= 16 ms AND frax median >= 30 ms at the same K, T): **FAIL** at T = 100 (it holds up to T = 50, see the sweep; the 2 s horizon was chosen for the video over the 50 Hz budget).
